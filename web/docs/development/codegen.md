# Code generation

One thing is generated and committed: the Postgres data-access layer, via sqlc.
Run it with:

```sh
make generate
```

The target has two lines. The sqlc line is the one that does real work; read the
[OpenAPI](#openapi-is-not-generated) caveat below before trusting the second.

## sqlc — the DB layer

```
db/queries/*.sql   ──┐
                     ├─ sqlc ─→ gen/sqlc/*.go   (committed)
db/migrations/*.sql ─┘
```

`sqlc.yaml` drives it:

- `queries: db/queries` — the hand-written SQL (`artifacts.sql`, `comments.sql`,
  `device_auth.sql`, `idempotency.sql`, `mcp_oauth.sql`).
- `schema: db/migrations` — sqlc reads the goose migrations to know the table
  shapes. The migrations are the schema source of truth.
- `out: gen/sqlc`, `package: sqlc`, `sql_package: pgx/v5`.
- Type overrides: `artifacts.metadata` and `comment_threads.anchor` →
  `encoding/json.RawMessage`; `sha256` columns rename to `SHA256`.

The output is **committed** to `gen/sqlc/` (`models.go`, `db.go`, one
`*.sql.go` per query file), each marked `// Code generated by sqlc. DO NOT EDIT.`.
`internal/store/pgstore` composes these queries with a `blob.Store`.

### Changing a query or the schema

1. Add a migration in `db/migrations/` (see
   [Extending arti](extending.md#a-new-db-migration)) and/or edit the SQL in
   `db/queries/`.
2. Apply the migration so your local DB matches: `make migrate` (and
   `make migrate-test`).
3. Regenerate: `make generate`.
4. Use the new generated method from `pgstore`, build, and test.
5. Commit the `gen/sqlc/` diff alongside your SQL change.

Never hand-edit files in `gen/sqlc/`; they're overwritten on the next run.

## OpenAPI is not generated

`make generate`'s second line is:

```sh
oapi-codegen --config=api/openapi/oapi-codegen.yaml api/openapi/openapi.yaml
```

Those paths **do not exist** in the tree, and no oapi-codegen output is committed
anywhere — the only generated Go is sqlc's. In practice this line is a no-op /
stale; the REST handlers are hand-written in `internal/artifacts/server.go`, not
generated from a spec.

The actual OpenAPI 3.0 spec lives at `cmd/arti-server/openapi.yaml`. It is
**hand-maintained**, embedded into the binary with `//go:embed`
(`cmd/arti-server/openapi.go`), and served verbatim at `/openapi.yaml`. Nothing
generates it from the Go code, and nothing generates Go from it. When you add or
change a REST endpoint, edit the handler **and** edit `cmd/arti-server/openapi.yaml`
by hand to keep them in sync. See [Extending arti](extending.md#a-new-rest-endpoint).

> Some other docs and the README describe `api/openapi/openapi.yaml` and "CI
> verifies no diff" on generated code. That's aspirational, not current: there is
> no `api/openapi/` directory, and CI has no `make generate`-and-diff step.
> Treat `cmd/arti-server/openapi.yaml` as the spec and keep `gen/sqlc/` in
> sync by hand.

## Tooling

`make setup` checks that `sqlc`, `goose`, and `oapi-codegen` are on `PATH` (see
[Local setup](local-setup.md#prerequisites)). Only `sqlc` is needed for the
generation that actually happens; `goose` runs migrations; `oapi-codegen` is
checked for but effectively unused given the note above.
